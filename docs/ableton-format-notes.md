# Ableton Live .als Format — Reverse-Engineering Notes

**Status:** Partially verified. Items marked ✅ VERIFIED were confirmed by direct testing with real `.als` files. Items marked ⚠️ UNVERIFIED come from public reverse-engineering sources and have not been tested against this project's Ableton installation.

---

## 1. Container format

- `.als` files are **gzip-compressed XML** (deflate/zlib stream inside a gzip wrapper).
- Decompress: `gunzip -c file.als > file.xml` (or Python `gzip` module).
- Recompress: gzip the XML back to `.als`. Ableton can also load **uncompressed XML renamed to `.als`**, which simplifies round-trip testing.
- Root element: `<Ableton MajorVersion="..." MinorVersion="...">` wrapping `<LiveSet>`.
- Live 11 and Live 12 use different `MinorVersion` headers.

⚠️ **UNVERIFIED:** Whether Ableton validates internal checksums. Current evidence suggests no checksum complaint on simple edits, but "invalid file structure" is possible if an injected value breaks structural logic expected by a node.

## 2. Track names (✅ VERIFIED by user)

Tracks live under `<LiveSet><Tracks>` and are typed:
`<AudioTrack>`, `<MidiTrack>`, `<GroupTrack>`, `<ReturnTrack>`.

Track name is stored in a mandatory `<Name>` parent block:

```xml
<Name>
  <EffectiveName Value="Bass Synth" />   <!-- auto-generated by default -->
  <UserName Value="" />                   <!-- empty by default; set on rename -->
</Name>
```

✅ **VERIFIED:**
- `<UserName>` and `<EffectiveName>` are hardcoded boilerplate in the mandatory `<Name>` block for **every** track component, regardless of creator.
- By default, `EffectiveName` contains an auto-generated value and `UserName` is empty.
- If the user renames a track, that name is set as the value of `UserName`.
- When both are present, Ableton **strictly prioritizes `<UserName>`** — the UI displays whatever string is inside `<UserName>`. If only one is present, the UI displays that value.

**Practical implication:** To match a track by artist-provided instrument name, read `<UserName>` first; fall back to `<EffectiveName>` if `UserName` is empty. To rename, set `<UserName Value="...">`.

Source: User-verified (manual test with real `.als` file).

## 3. Static mixer volume (✅ VERIFIED element path and edit safety)

The static (manual) track fader / gain is stored here:

```xml
<DeviceChain>
  <Mixer>
    <Volume>
      <Manual Value="0.3162277937" />   <!-- linear gain, NOT dB -->
    </Volume>
  </Mixer>
</DeviceChain>
```

Format details:
- **Linear scale**, not dB. `1.0 = 0 dB (unity gain)`.
- Conversion: `linear = 10^(dB / 20)`, `dB = 20 × log10(linear)`.
- Observed values:
  - `0.0003162277571` ≈ −70 dB (effectively off / minimum)
  - `0.3162277937` = −10 dB
  - `0.5` = −6 dB
  - `1.0` = 0 dB (unity)
  - `1.99526238` = +6 dB (maximum)

✅ **VERIFIED:**
- **No checksum complaints:** Ableton will not complain about checksums when editing `<Manual Value>`. As long as the file is correctly gzipped and the XML remains well-formed, Live parses the edited value natively.
- **Invalid file structure:** Ableton *can* complain about "invalid file structure" if the injected value breaks the structural logic expected by that specific node (e.g., out-of-range or malformed value).
- **Multiple independent versions:** You can generate v1.als, v2.als, etc. from the same baseline; each is self-contained and reopens flawlessly. .als files are independent instructions — no shared state between versions.

⚠️ **UNVERIFIED:** Whether extreme values (beyond hard bounds) trigger "invalid file structure."

Live Object Model (M4L / Python MIDI Remote Scripts) path:
`live_set tracks <track_index> mixer_device volume`

## 4. Volume bounds (✅ VERIFIED by user)

Track volume parameters are **hard-bounded**:
- **Maximum:** +6.02 dB (linear ≈ 1.99526238)
- **Minimum:** −inf dB (maps mathematically to roughly −70 dB or lower)

**Practical implication:** The MVP must clamp requested dB changes to [−70 dB, +6.02 dB] before writing to the `.als`. Requests outside this range should be rejected as invalid.

Source: User-verified.

## 5. Volume automation vs. static volume (⚠️ UNVERIFIED for this MVP)

Automation is stored separately from the static mixer volume:

```xml
<Automation>
  <Events>
    <FloatEvent Id="..." Time="..." Value="..." />
  </Events>
</Automation>
```

- Each automation event is tied to a parameter via `AutomationTarget Id="X"`.
- `AutomationTarget` IDs must be **unique across the entire file**.
- `NextPointeeId` must be higher than **all** IDs in the file.

**MVP scoping decision:** Per user direction, the MVP only changes **static mixer volume for a single track**. Downstream automation impact is explicitly out of scope and not analyzed here. We do not modify automation lanes.

Source: [Menke Technologies ALS Generation Findings — Automation & Target ID Management](https://menketechnologies.github.io/MenkeTechnologiesMeta/Audio-Haxor/ALS_GENERATION_FINDINGS.md)

## 6. Version compatibility (✅ VERIFIED by user)

✅ **VERIFIED:** Ableton follows a **one-way backward compatibility** rule:
- **Live 12 opens Live 11 `.als` files seamlessly** (forward compatibility).
- **Live 11 does NOT open Live 12 `.als` files** (reverse not supported).

**MVP target:** Live 12 (majority of active users). Editing a Live 11 file is safe to open in Live 12; editing a Live 12 file may break opening in Live 11. The MVP should document which Live version produced each baseline `.als`.

Source: User-verified.

## 7. Direct .als editing — reliability assessment

### What is verified
- ✅ Decompress → edit `<Mixer><Volume><Manual Value>` → recompress → `.als` opens in Ableton with the new volume.
- ✅ No checksum complaints on simple value edits (correctly gzipped + well-formed XML is sufficient).
- ✅ Multiple version files from one baseline all reopen independently.
- ✅ Ableton accepts uncompressed XML renamed to `.als` (useful for testing).
- ✅ Third-party parsers exist (abletoolz, pyableton, dawtool).

### What remains risky
- ⚠️ **"Invalid file structure":** Possible if injected value breaks structural logic expected by a node. Mitigated by clamping to verified bounds [−70 dB, +6.02 dB].
- ⚠️ **ID collisions:** If the MVP ever introduces new IDs (e.g., automation targets), they must be unique; `NextPointeeId` must stay above all IDs. The MVP does not introduce new IDs — it only edits existing `<Manual Value>`.
- ⚠️ **Programmatically injected device XML is reportedly rejected** by Ableton's parser in some cases (e.g., sidechain compressors, master EQ8/limiter). The `<Mixer><Volume><Manual>` element is core and simple, so it is more tolerant — verified by direct test.
- ⚠️ **Live version matrix:** Must target Live 12; reverse compatibility with Live 11 is not supported.

### Bottom line
Direct `.als` editing of static mixer volume is **verified to work** and is the **simplest** approach for a Python MVP (no running Live instance required). The main risks are value bounds (mitigated by clamping) and Live version compatibility (mitigated by targeting Live 12). This is the recommended approach for the MVP.
